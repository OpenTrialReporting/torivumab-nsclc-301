## 1. Disclosure

`define/arm.xml` is a v0.1 (pilot) Analysis Results Metadata (ARM) file supporting a
**fully synthetic** clinical trial dataset generated for educational purposes. No real
trial is described. All sponsor names, drug names, and study identifiers are fictional.

The ARM file structure is grounded in the CDISC ARM v1.0 specification (extension to
Define-XML v2.x) but has not been validated against a regulatory authority, P21
Enterprise, or any commercial ARM validator. It has not been submitted to FDA, PMDA,
or any other agency.

## 5. Deferred to v0.2 (and rationale)

The v0.2 punch list. Each item is a deliberate omission with a clear rationale; v0.2 closes them.

### D-ARM-01: WhereClauseRef for analysis-set semantics — deferred

**v0.1 behaviour:** Analysis-set filtering (e.g. ITT, SAFETY, PARAMCD='OS') is described in `arm:Documentation` prose only — no machine-readable filter binding.

**Why deferred:** Emitting `<def:WhereClauseRef>` requires the target WhereClause OIDs to first exist in `define/define.xml` (`<def:WhereClauseDef>`). The current `build_define.R` does not enumerate analysis-set or PARAMCD filter combinations as named WhereClauses. Adding them is mechanical but couples ARM scope to Define scope.

**v0.2 action:**
1. Extend `build_define.R` to emit `<def:WhereClauseDef OID="WC.<DS>.<SET>[.<PARAM>]">` for each (dataset × analysis_set × parameter_code) combination used by any output. Estimated: ~25 WhereClauses (5 analysis sets × ~5 PARAMCD families).
2. Update `build_arm.R` to emit `<def:WhereClauseRef>` inside each `<arm:AnalysisDataset>` block.

### D-ARM-02: AnalysisVariable per-dataset attribution — partial

**v0.1 behaviour:** `key_variables` from `shells.yaml` are attached to the **first** `arm:AnalysisDataset` block only. When an output draws from multiple source datasets (e.g. ADTTE + ADSL for stratified Cox), the variables are nominally bound to the first dataset even though some live in the second.

**Why deferred:** `shells.yaml` schema has a flat `key_variables:` list, not a `{dataset: [vars]}` map. Disambiguation requires either:
- Schema extension (`key_variables_by_dataset:`), or
- Inference from each variable's home dataset via per-dataset specs in `programming-specs/`.

Either approach is straightforward but a schema decision that should be made deliberately rather than back-doored through this pilot.

**v0.2 action:** Extend `shells.yaml` `outputs[].key_variables` from list to map; update `render_shells.R` and `build_arm.R` accordingly. Backward compatibility shim: if value is a list, attribute to first dataset (current behaviour).

### D-ARM-03: Inline programming code vs file reference — file-ref only

**v0.1 behaviour:** `<arm:ProgrammingCode><arm:Code>` contains only `Rscript programs/tfl/<script>.R`, plus a `<def:DocumentRef>` leaf to the script. The actual derivation R code is not inlined.

**Why deferred:** Sponsor practice varies. FDA reviewers can follow leaf references; embedding ~50–200 lines of R per output inflates `arm.xml` by ~30× with information already in the script. For pilot purposes the leaf reference is sufficient.

**v0.2 action (optional):** For the SAP-primary subset (T-EFF-01, T-EFF-03, F-EFF-01, F-EFF-02), inline the core analysis call (`coxph(...)`, `survfit(...)`) inside `<arm:Code>` as a 1–5-line snippet, alongside the existing leaf reference. Leaves the index format unchanged.

### D-ARM-04: Cross-binding to define.xml OIDs — symbolic only

**v0.1 behaviour:** `arm.xml` uses `ItemGroupOID="IG.<DS>"` and `ItemOID="IT.<DS>.<VAR>"` matching the naming convention in `build_define.R`. There is no automated check that every referenced OID actually exists in `define.xml`.

**Why deferred:** A round-trip validator is straightforward but separate work. v0.1 trusts the naming convention.

**v0.2 action:** Add a `validate_arm.R` script that loads both `arm.xml` and `define.xml`, resolves every `ItemGroupOID` / `ItemOID` / `WhereClauseOID` reference, and reports unresolved IDs. Run it from `programs/qc/run_reproducibility_check.R` as part of the define step.

### D-ARM-05: Methods catalogue not structured — free-text prose

**v0.1 behaviour:** `o$methods` (e.g. `[M-COX-STRAT, M-KM-MEDIAN]`) is rendered as comma-separated text inside `arm:Documentation`. The methods catalogue in `shells.yaml` (18 methods) is not surfaced as structured ARM content.

**Why deferred:** ARM v1.0 does not have a dedicated `<arm:Method>` element; methods typically appear in CodeLists or Documentation. ARS v1.0 *does* introduce structured methods. A v0.2 here can do one of:
- Stay in Documentation prose (current).
- Emit a `<def:CodeList OID="CL.METHODS">` enumerating method IDs, and reference them by OID.
- Skip ahead to ARS for methods (see D-ARM-06).

**v0.2 action:** Choose at v0.2 review; default = stay in prose, add `<def:CodeList>` only if a reviewer asks.

### D-ARM-06: ARS migration path — out of scope for v0.x

**v0.1 behaviour:** ARM v1.0 chosen over CDISC ARS v1.0 (Analysis Results Standard, the successor).

**Why:** ARM v1.0 has stable tooling (P21 Enterprise validation, established submission patterns); ARS v1.0 is newer and validator support is still maturing. A real first submission would choose ARM v1.0 today; ARS becomes relevant for studies starting Phase 6 in 2027+.

**v0.2 / v1.0 action:** Decide whether to dual-emit ARM + ARS or migrate. No work needed for v0.2 of this study.

## 7. Architecture Decisions

### D-ARM-07: `arm.xml` as a separate file, not embedded in `define.xml`

**Decision:** `define/arm.xml` is its own ODM file rather than an `<arm:AnalysisResultDisplays>` block inside `define/define.xml`.

**Why:** Allows ARM and Define to iterate on independent cadences. Define-XML is regenerated when the data structure changes; ARM is regenerated when the analysis catalogue changes. Coupling them forces full re-rendering on every TFL shell change.

**Rejected alternative:** Embed in `define.xml`. Simpler tree, but every TFL-shell change re-renders the dataset metadata.

### D-ARM-08: `shells.yaml` as the source of truth for ARM content

**Decision:** `build_arm.R` reads `sap/shells/shells.yaml` exclusively; no manual ARM editing.

**Why:** `shells.yaml` is already SAP-locked at Gate 3.5 and is the source for `TFL-SHELLS.md`, `TFL-SHELLS-DOC.docx`, and the TFL R scripts' shell references. Single source of truth prevents three-way drift.

**Constraint this imposes:** Any ARM-only metadata (e.g. `reason`, `purpose`) must be added to `shells.yaml`, not to a sidecar. This is why §5's deferred items will all touch `shells.yaml` schema.
